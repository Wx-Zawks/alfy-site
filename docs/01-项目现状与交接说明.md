## 4. SEO 实现与配置

后台“SEO 管理”提供全局配置、固定页面、页面 SEO、重定向及 404 记录；全局设置修改受超级管理员权限控制。

- `useGlobalSeo.ts` / `usePageSeo.ts`：全局及栏目设置，标题、描述、索引规则、canonical 和分享信息。
- `app.vue` 及详情页：Organization、WebSite、Product、Article、BreadcrumbList 等 JSON-LD。
- `server/routes/robots.txt.ts`、`sitemap.xml.ts`：动态规则与已发布 URL，旧静态文件已删除。
- `server/middleware/seo-redirect.ts`：后台维护的 301/308 跳转，支持主机匹配、参数保留和命中记录。
- 后台及错误页禁止索引；统计插件支持电话、邮件、咨询、下载及询盘来源归因，需配置后才启用。

生产 Compose 显式传入 SSR 内部 API 地址 `http://api:8080/api/v1` 和浏览器同域地址 `/api/v1`，以及 `NUXT_PUBLIC_SITE_ORIGIN`、`NUXT_PUBLIC_SITE_INDEX_ENABLED`。正式站索引开关应为 true，本地、测试及预发布必须显式设为 false；后台“允许索引”也要开启。

公开 SEO 接口为 `/api/v1/public/seo/settings`、`/routes`、`/urls`，重定向解析为 `/api/v1/public/redirects/resolve`。

**既有待办：** robots 仍禁止 `/api/`，公开图片却使用 `/api/v1/public/media/…`。普通图片访问成功不代表爬虫获准抓取；公开媒体抓取例外仍需单独评估，不得误称已解决。

## 7. 四仓库协作边界

| 远程 | 地址 | 边界 |
|---|---|---|
| `origin` | https://github.com/Wx-Zawks/alfy-site.git | monorepo：集成、部署配置、文档和发布记录 |
| `source-web` | https://github.com/1sheep1/alfy-web.git | 根目录对应 `afly-web/` |
| `source-admin` | https://github.com/1sheep1/alfy-admin.git | 根目录对应 `alfy-admin/` |
| `source-api` | https://github.com/1sheep1/alfy-api.git | 根目录对应 `alfy-api/` |

三个应用各自 main 是日常功能基线，origin/main 是集成和发布记录；根目录和历史不同，不能直接混合。

1. 工作前检查本机改动及未跟踪文件，再 fetch 相关远程。
2. 审查应用 main 的差异，映射到集成子目录，处理冲突、构建和测试。
3. 使用 `codex/…` 分支与正常 PR；不覆盖或强推同门 main。
4. 反向同步修复时，在对应独立工作区建立审查分支，只回传该应用文件。
5. 部署文件和文档只同步 origin，不把证书、生产环境变量、数据库、上传卷或服务器私有备份推送到任何仓库。
6. 服务器热修复必须回写本机及应同步仓库，并记录文件、提交和验收；生产服务器不能成为唯一源码副本。

禁止在 monorepo 或生产服务器对 source-* 执行 pull/merge；禁止全仓覆盖服务器。发生本机冲突时先备份；旧本机交接说明保留在 `output/sync-20261103/handoff.local-before.md`。

## 8. 发布与检查

生产环境文件 `/opt/alfy-site/deploy/.env.production` 权限 600。不得将内容输出聊天、下载或提交，不展开全量 Compose 环境值用于常规检查。

```bash
cd /opt/alfy-site/deploy
docker compose --env-file .env.production config --quiet
docker compose --env-file .env.production ps
docker exec alfy-nginx nginx -t
curl --resolve www.alfy.com.cn:443:127.0.0.1 https://www.alfy.com.cn/api/v1/health
docker compose --env-file .env.production logs --tail=100 api
```

发布顺序：确认授权、生产身份和实际基线 -> 核对迁移及备份数据库/明确文件/旧镜像 -> 精确同步 -> 配置检查及构建 -> 按依赖顺序切换 -> 重启 Nginx 刷新上游解析 -> 业务和数据验收 -> 回写仓库与记录。

- 仅更新受影响服务，不全量重建；API 地址变化及 web/admin 重建后均检查 Nginx 上游解析。
- 仅替换已挂载证书或配置，检查后 reload；Compose 端口、挂载变化需要更新 Nginx 容器。
- HTTP 200、健康接口或构建成功不能代替后台编辑、媒体和移动端业务验证。
- 禁止 `docker compose down -v`、`docker system prune -a`、`git reset --hard` 和未经核对的递归删除。
