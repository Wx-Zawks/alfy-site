## 1. 项目组成

| 目录 | 应用 | 技术栈 | 生产职责 |
|---|---|---|---|
| `afly-web` | 官网展示端 | Nuxt 3、Node.js 22、SSR | 对外官网 |
| `alfy-admin` | CMS 管理后台 | Vue 3、Vite、Vben、pnpm、Element Plus | 内容、素材、页面管理 |
| `alfy-api` | 后端 API | Java 17、Spring Boot 3.5.16、Spring Security、MyBatis-Plus、Flyway | 认证、CMS、文件上传、API |
| `deploy` | 生产编排 | Docker Compose、Nginx、MySQL 8.4 | 容器和反向代理配置 |

项目采用单台 ECS 的 Docker Compose 架构：

```text
浏览器
  -> Nginx（唯一正式公网入口：80/443）
      -> 官网 Nuxt 容器（web:3000）
      -> 管理后台静态容器（admin:80）
      -> Spring Boot API（api:8080）
          -> MySQL（db:3306）
```

正式域名规划：

- `alfy.com.cn` 与 `www.alfy.com.cn`：官网。
- `admin.alfy.com.cn`：管理后台。
- `api.alfy.com.cn`：可选的 API 调试入口；日常前端使用同域 `/api/v1`，无需暴露 API 端口。

## 4. 当前 Compose 与流量配置

### 正式入口

Nginx 根据 Host 分流：

- `alfy.com.cn` / `www.alfy.com.cn` 的 `/` -> `web:3000`。
- `admin.alfy.com.cn` 的 `/` -> `admin:80`。
- 各站点的 `/api/` -> `api:8080`。
- API、MySQL、Node 内部端口均不应直接暴露到公网。

数据库使用命名 volume：

```text
mysql_data    MySQL 数据
uploads_data  后端上传的素材
```

绝对不要用 `docker compose down -v` 清理生产环境；该命令会删除上述持久化卷。

### 临时后台演示入口

备案期间，IP:80 只会命中官网默认站点。为演示后台，已配置：

```text
http://<ECS公网IP>:18081
```

实现位置：

- `deploy/docker-compose.yml`：Nginx 映射 `18081:18081`。
- `deploy/nginx/http.conf`：`listen 18081` 的临时 server，`/` 转发后台，`/api/` 转发 API。
- API 的 `ALFY_WEB_ALLOWED_ORIGINS` 临时包含该 IP:18081 来源。

安全要求：

1. 安全组 TCP 18081 仅允许演示电脑当前公网 IP 的 `/32`。
2. 不允许将 18081 来源设置为 `0.0.0.0/0`。
3. 演示完成即暂停/删除安全组规则。
4. 备案完成、正式后台 HTTPS 可用后，删除 18081 端口映射、Nginx 临时 server 块和临时 CORS 来源，再执行 `docker compose up -d`。

## 5. 镜像和依赖下载策略

服务器曾出现 Docker Hub、npmjs、Maven Central 访问超时。当前成功构建依赖以下策略：

- Docker 基础镜像使用 `m.daocloud.io/docker.io/library/...`。
- 官网 Dockerfile 设置 `npm_config_registry=https://registry.npmmirror.com`。
- 管理后台 Dockerfile 设置 `COREPACK_NPM_REGISTRY` 与 `npm_config_registry`。
- 后端使用 `alfy-api/.mvn/settings.xml` 中的阿里云 Maven 公共仓库。
- Maven Wrapper 分发包地址也指向阿里云 Maven 公共仓库。

长期生产建议：把已验证的基础镜像同步到公司自己的阿里云 ACR，并固定版本或摘要，避免依赖第三方公共镜像站。

## 6. 曾发生的重要问题

### 6.1 源码 `src/data` 被误忽略

根目录原有 `**/data/` 规则，会误伤：

```text
alfy-admin/apps/web-ele/src/data/cms.ts
alfy-admin/apps/web-ele/src/data/cms-adapter.ts
```

缺失时，Vite 会报 `Could not load .../src/data/cms` 或 `cms-adapter`。现已在根 `.gitignore` 加入反向规则，并恢复 `cms-adapter.ts`。

后续提交前必须检查：

```powershell
git status --short
git check-ignore -v alfy-admin/apps/web-ele/src/data/cms.ts
```

这两个文件必须纳入 Git，不能再仅存在于某台服务器。

### 6.2 非 UTF-8 文件名

`alfy-admin/docs` 内曾存在非 UTF-8 文件名，Docker BuildKit 报：

```text
grpc: failed to unmarshal the received message: string field contains invalid UTF-8
```

已将 `docs/` 写入 `alfy-admin/.dockerignore`。该目录不参与后台构建。

## 12. Git 仓库、协作关系与同步边界

### 12.1 仓库角色

| 仓库/远程名 | 地址 | 作用 |
|---|---|---|
| `origin` | `https://github.com/Wx-Zawks/alfy-site.git` | 当前部署使用的**单仓库集成版本**，含三个应用和 `deploy`、文档；生产发布的唯一依据。 |
| `source-web` | `https://github.com/1sheep1/alfy-web.git` | 同门维护的官网独立仓库。 |
| `source-admin` | `https://github.com/1sheep1/alfy-admin.git` | 同门维护的后台独立仓库。 |
| `source-api` | `https://github.com/1sheep1/alfy-api.git` | 同门维护的 API 独立仓库。 |

同门已给当前维护者三个 `source-*` 仓库的 Git 权限。此前已把本项目对应代码发送到对方的 `sync/alfy-site-20260809` 分支；后台和 API 的 `main` 已快进合并，官网的对应合并由同门完成。

### 12.2 绝对不能直接执行的同步方式

这四个仓库不是同一个 Git 历史：`origin` 是 monorepo，`source-web` / `source-admin` / `source-api` 分别以各自应用目录为仓库根目录。因此：

- 不要在 `/opt/alfy-site` 或本地 monorepo 中对 `source-*` 执行 `git pull`。
- 不要把 `source-web/main` 直接 merge 到 monorepo `main`。
- 不要为了“同步”在服务器执行 `git reset --hard`、`git restore .` 或覆盖整个项目目录。

这些操作会因目录根目录不同而制造大量删除/冲突，甚至覆盖生产端未纳入 Git 的环境文件或临时配置。

### 12.3 正确的日常协作流程

```text
同门在独立应用仓库开发
  -> 提交并推送其 feature/main 分支
  -> 本项目维护者 fetch 对应 source-* 远程
  -> 将“应用仓库根目录”的变更映射到 monorepo 的 alfy-web/、alfy-admin/ 或 alfy-api/ 子目录
  -> 在 origin 的集成分支解决冲突、构建和测试
  -> 合并/推送到 origin/main，记录提交号
  -> 服务器按精确文件同步，备份后仅重建受影响服务
```

反向同步也同理：先从 `origin/main` 中挑选某个应用目录的已验证变更，生成对方独立仓库可审查的同步分支或 PR，再由仓库负责人合并。除非双方明确确认是快进且无需审查，不要直接推送他人的 `main`。

建议长期治理：指定一个唯一的“发布源”（推荐 `origin/main`），并让三个独立应用仓库通过同步分支/PR 与其对接；更进一步可把 monorepo 改为 Git submodule、subtree 或统一为单一 monorepo，但这是架构迁移，必须先备份和制定迁移方案，不能临时操作。

### 12.4 常用只读检查

在本地 monorepo：

```powershell
git status --short
git log --oneline -8
git remote -v
git fetch source-web source-admin source-api --prune
git branch -r
```

`git fetch` 只更新本地远程跟踪信息，不会改工作区；在判断要合并哪些文件前应先执行它。涉及 push、merge、服务器更新或数据库迁移时，必须先确认目标分支、变更范围和回滚方式。

## 13. 服务器代码更新的安全流程（本项目专用）

服务器上的 `/opt/alfy-site` 最初由压缩包上传形成，之后才接入 Git；它可能含有历史文件差异。因此服务器不是普通干净 clone，不能直接用 `git pull` 覆盖。

推荐按下列流程更新。以下以官网更新为例，后台/API 只需替换路径和服务名：

```bash
# 0. 登录后确认位置与当前状态（只读）
cd /opt/alfy-site
git status --short
git log --oneline -5

# 1. 获取远程提交信息；不直接改变工作区
git fetch origin main
git show --stat <准备发布的提交>

# 2. 只备份本次要替换的文件；backup_dir 必须是新目录
backup_dir="$HOME/alfy-site-backup-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
for file in \
  afly-web/nuxt.config.ts \
  afly-web/pages/index.vue; do
  [ -e "$file" ] && cp --parents "$file" "$backup_dir"
done
echo "备份目录：$backup_dir"

# 3. 仅从已确认的提交恢复明确列出的文件
git restore --source=<准备发布的提交> -- \
  afly-web/nuxt.config.ts \
  afly-web/pages/index.vue

# 4. 先校验 Compose，再只重建官网
cd /opt/alfy-site/deploy
sudo docker compose --env-file .env.production config --quiet
sudo docker compose --env-file .env.production up -d --build web

# 5. 验证
sudo docker compose --env-file .env.production ps
curl -i --max-time 10 http://127.0.0.1/api/v1/health
```

服务对应关系：

| 变更目录 | 通常重建命令最后的服务名 | 必做额外检查 |
|---|---|---|
| `afly-web/` | `web` | 官网 PC 与移动端、SSR 页面数据、媒体 URL。 |
| `alfy-admin/` | `admin` | 后台静态页、登录、上传和 CMS 编辑。 |
| `alfy-api/` | `api` | 健康检查、日志、Flyway 迁移和 API 兼容性。 |
| `deploy/` | 视配置而定，通常 `nginx` 或全部 `up -d` | `config --quiet` 必须先返回 0；检查端口和代理。 |

API 变更若包含 Flyway 数据库迁移，发布前先备份数据库，审查 SQL 是否可回退；容器镜像回滚不能自动撤销已经执行的数据迁移。

4. 不用 `docker compose down -v`、`docker system prune -a`、递归删除或 `git reset --hard` 处理“部署失败”。先看 `docker compose logs` 和构建错误。
5. 不以“配置文件语法正确”代替业务验证：必须检查容器、健康接口、官网、后台和手机端。
6. 备案未完成期间，域名访问出现阿里云备案拦截页是预期合规行为；不要通过长期修改 hosts、公开临时端口或绕过备案来运营网站。
7. 任何协作同步先明确“哪个仓库、哪个分支、哪些目录、哪个提交、是否已测试”，再执行 merge/push/deploy。
